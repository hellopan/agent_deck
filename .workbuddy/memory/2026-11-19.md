## 窗口阴影：CS_DROPSHADOW → DWM 真窗口阴影

用户指出「四周应有薄阴影，现在只有右侧和底边有实阴影」。

### 根因

`WebViewWindow.CreateParams` 里加了 `CS_DROPSHADOW`（0x20000）。这是 Win95 时代的替代方案：光源在左上，只画右/下两条硬边，左/上完全没有，且是实边不是渐变。

### 修法（`WebViewWindow.cs`）

- 删掉 `CreateParams` 覆写与 `CS_DROPSHADOW`。
- `OnHandleCreated` → `ApplyWindowFrame()`：
  - `DwmExtendFrameIntoClientArea(hwnd, MARGINS{1,1,1,1})` — 让 WS_POPUP 窗口拥有 frame，DWM 才会按普通窗口画阴影。
  - `DWMWA_NCRENDERING_POLICY=2`（DWMNCRP_ENABLED）。
  - `DWMWA_WINDOW_CORNER_PREFERENCE=2`（DWMWCP_ROUND）— Win11 系统圆角 8px。
  - `DWMWA_BORDER_COLOR=0x00DED9D5` — 正好是设计稿 `--app-border: #d5d9de`。
- 顺带修：WS_POPUP 最大化会铺满整屏盖住任务栏（实测 2560x1440）。`WndProc` 应答 `WM_GETMINMAXINFO(0x0024)`，把 `MaxPosition/MaxSize` 改成工作区 → 2560x1392。

### 量化验证（`.shots/win.ps1` + `px.ps1` 的 `prof`/`px`）

窗口外 1px 处亮度：左 210 / 右 210 / 上 230 / 下 181，背景 250-253。四边都有 20-40px 渐变过渡；上下略强/略弱是 DWM 的向下偏移，属正常。四边 `#D5D9DE` 边框完全一致，四角被系统裁圆（角落像素是阴影色而非边框色）。

`.shots/win.ps1`：桌面级截图（`Graphics.CopyFromScreen` + `GetWindowRect` + `SetProcessDPIAware`），页面截图 `Page.captureScreenshot` 抓不到窗口外沿的阴影。

## 配对窗口被主窗口盖住（无属主弹窗）

用户：设置-配对-生成配对码，二维码闪一下就沉到主窗口后面。

### 根因

`DeckBridge.PairAsync` 用 `dialog.ShowDialog()`（**没有 owner**）。`ShowDialog()` 的无参重载只是把窗口标成模态，z-order 上和主窗口没有关系；主窗口一旦激活就盖上去。而 `AGENTDECK_SHOW=1` 会把主窗口设成 `TopMost`，TopMost 是独立的 z-order 层，属主链也救不了——弹窗必然在下面。

### 修法（`DeckBridge.cs`）

- 新增 `internal Form? Owner { get; set; }`，`WebViewWindow` 构造时 `bridge.Owner = this`。
- `ShowOwned(dialog)`：有属主就 `ShowDialog(owner)`（顺带把 `CenterParent` 变成真正的主窗口居中），属主是 TopMost 时把弹窗也设 TopMost。
- `Ask(...)`：所有 `MessageBox.Show` 改走属主重载（服务装卸、改钉证书确认）。
- 三处弹窗全部接入：`PairingWindow`、`RelayWindow`、`ProjectEditor`。
- `Program.RunShell` 的 QA 钩子改成 `TopMost=true; TopMost=false`：只抬一次到前台，不再长期占据最顶层（长期置顶既压住别的程序，也让自己的弹窗跑到下面）。

### 验证（`.shots/wins.ps1` 枚举顶层窗口）

配对窗口 `vis=True rect=3522,346 636x699`，主窗口 `3250,262 1180x868`，两者都 `topmost=False`；EnumWindows 顺序里配对窗口排第一（z-order 最上），居中偏移 (1180-636)/2=272 与 (868-699)/2=84 完全吻合 —— 确认是属主关系而不是碰巧抬到前面。

### 顺带发现（未修）

`PairingWindow` 仍是 WinForms 老样式（原生小标题栏、GDI 字），夹在 HTML 外壳里风格割裂。要统一得把配对流程搬进页面（二维码用 canvas 画、候选轮询走桥）。

## 配对流程从 WinForms 弹窗搬进页面（v3 适配）

- `pairPane()`：空态是虚线方块 + 「生成配对码」；生成后换成 `<img>` + `mm:ss` 倒计时，按钮文案改「重新生成」。
- 轮询每 1.2s 一次，命中候选 → `openPairSheet(fingerprint)` 弹确认层。
- 确认层 `.scrim` 是页面内 fixed 遮罩 + 白卡片，不是窗口。**遮罩从标题栏下沿开始**（`top:38px`）：WebView2 把 `app-region: drag` 实现成原生非客户区，绘制在 DOM 之上，`inset:0` 的遮罩盖不住它，硬盖反而会出现"标题栏没变暗"的割裂感。
- 指纹按**每行 4 组、每组 4 位十六进制**重排（与手机端一致），32 字节正好 4 行；后端可能给冒号、空格或裸 hex，先 `replace(/[^0-9A-F]/g,"")` 再分组。

### 修掉一个真 bug

`pairTick()` 里 `if (!pair.waiting || Date.now() < pair.nextPoll) return;` —— `waiting` 初始是 `false`，所以第一帧就 return，**永远不会发起第一次轮询**。改成只在 `Date.now() < nextPoll` 时 return。

## 配对二维码扫不出来：密度诊断与显示修复

用户：二维码点太密，手机扫不出来，问能不能扫码后先连上再传 relay 信息。

### 实测数据（不是猜测）

`pair-invite` 实际输出 **1640 字节**：

| 字段 | 字节 | 说明 |
|---|---|---|
| `entry.peerCertificate` | 635 | 主机身份证书 PEM |
| `relayCertificate` | 542 | Relay 证书 PEM |
| `code` / `entry.token` | 64 / 64 | hex |
| `device` / `relayUrl` / `host` | 32 / 23 / 8 | |
| JSON 键名与标点 | ~272 | |

1640 字节 @ ECC L → **版本 29，149×149 模块**（含 4 模块静区 157）。`GetGraphic(4)` 生成 628px PNG，但页面里：内嵌方块 176px → **1.12 px/模块**，放大层 320px → **2.04 px/模块**。手机扫描的comfort阈值是 ≥3。所以不是"手机不行"，是每个模块不到 2 个像素。

### 能搬走什么、不能搬走什么

- **必须留在二维码里**：`relayUrl` + `entry.token`（23+64 字节）。手机要靠它找到 Relay 并认证路由，没有就没法"先连上"。剩下的 `device`/`code` 也是寻址必需。

## 手机配对失败的真正原因（AndroidKeyStore 摘要 + Relay 单隧道竞态）

### 如何拿到真凭据：装 JDK + 跑模拟器

### 根因一：AndroidKeyStore 不允许 NONE 摘要

模拟器复现出完整堆栈：

```
Caused by: android.security.KeyStoreException: Incompatible digest (code -13)
  at AndroidKeyStoreSignatureSpiBase.ensureKeystoreOperationInitialized
  at ...NativeCrypto.ENGINE_SSL_read_direct
  at RelayClient.query(RelayClient.kt:160)
  at PairingKt.requestPairing(Pairing.kt:44)
```

Conscrypt 在 TLS 1.3 里通过 BoringSSL 把**已算好的摘要**交给私钥签名（NONE 方式），而 `Pairing.kt` 生成密钥时只授权了 SHA256/384/512，KeyStore 直接拒绝。**修法：`setDigests` 里加上 `KeyProperties.DIGEST_NONE`。** 这与网络、证书、Relay 都无关——之前所有"手机到 Relay 不通"的推断都是被这条报错的表层文字带偏的。

### 根因二：Relay 单隧道 + Agent 250ms 重连空窗

修完签名后配对成功，但轮询一直"连不上"。新加的诊断一行说清：

```
Expected HTTP 101 response but was '503 Service Unavailable'
```

`relay.attachPhone` 要求 `tunnels[device]` 存在且 `!claimed`，而 Agent 每次会话结束要 250ms 才重新 dial。手机一次 `sync` 连发 `approvals` + `queue` 两条命令（每条一条隧道），第二条必然撞空窗。**修法：`RelayClient.query` 外层包一层重试，仅在消息含 `503` 时重试（升级前失败，命令没送达，对 approve 这类写操作也安全），300/600/900ms 共 3 次。**

更彻底的修法是让 `attachPhone` 在没隧道时短暂等待（2–3s）而不是立刻 503，但 Relay 在 8.159.131.11 上，本机没有 SSH 凭据，改不了；代码层面未动。
